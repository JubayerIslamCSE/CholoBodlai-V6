# CholoBodlai V6 — Your GitHub + Render + Cloudinary project

**Runtime:** Java 21 / Spring Boot 4.1.1 / MongoDB Atlas / Thymeleaf / Docker.
**Local:** `http://localhost:8080`.
**Public:** your Render HTTPS URL, e.g. `https://cholobodlai-v6.onrender.com` (only if assigned by Render).

This ZIP contains **project source**, NOT a published service, and contains **no MongoDB, Cloudinary, Render, or mail secret keys**. Keep your existing MongoDB Atlas database; no reset or migration is run on startup. The older app still works independently if you extract V6 to a new folder.

## 1 — IntelliJ IDEA: exact Run / Edit Configurations setup

1. Extract the ZIP. Open the **inner `CholoBodlai` folder containing `pom.xml`** using IntelliJ > File > Open.
2. Wait for Maven imports. Use IntelliJ Settings > Build Tools > Maven > **Bundled (Maven 3)** if your wrapper fails to sync.
3. Go to **Run > Edit Configurations > + > Application** (or Spring Boot if available).
4. Enter these fields:

| Field | Enter exactly |
|---|---|
| **Name** | `CholoBodlaiApplication` |
| **Run on** | Local machine |
| **JDK / Java SDK / JRE** | Java **21** |
| **Main class** | `com.jubayer.cholobodlai.CholoBodlaiApplication` |
| **Use classpath of module** | `CholoBodlai` module from the opened Maven project |
| **Working directory** | **Your extracted folder that contains `pom.xml`** (keep the IntelliJ default if it points there) |
| **Program arguments** | Leave **blank** |
| **VM options** | Leave **blank** |

5. In **Environment variables**, click the small edit icon and create separate **Name → Value** rows:

| Name | Value | Required locally? |
|---|---|---|
| `MONGODB_URI` | Your *existing working Atlas URI*, including the chosen database name | Yes (unless you deliberately use local MongoDB) |
| `APP_ADMIN_PHONE` | An admin phone number | For admin bootstrap |
| `APP_ADMIN_PASSWORD` | A private password **10+ characters** | For a *new* admin bootstrap |
| `APP_JWT_SECRET` | Secret generated by `openssl rand -hex 32` | Recommended |
| `CLOUDINARY_CLOUD_NAME` | From Cloudinary Dashboard | Recommended so you test uploads before deployment |
| `CLOUDINARY_API_KEY` | From Cloudinary Dashboard | With Cloudinary cloud name |
| `CLOUDINARY_API_SECRET` | From Cloudinary Dashboard | With the key |
| `APP_MEDIA_BACKEND` | `cloudinary` (or `auto` for optional local-only fallback) | Recommended `cloudinary` |
| `APP_PUBLIC_BASE_URL` | `http://localhost:8080` | Recommended for mail links |
| `APP_MAIL_PREVIEW` | `true` to test recovery links using the local admin-only demo mailbox | For local demo if no Resend |
| `APP_DEMO_SEED` | `false` (keep existing data) | Recommended |
| `APP_COOKIE_SECURE` | `false` for localhost HTTP | Recommended |
| `RESEND_API_KEY` | Optional real Resend HTTPS mail API key | Only if you want real emails locally |
| `APP_MAIL_FROM` | Your verified Resend sender address | With Resend key |

**Do not enter `PORT` locally**; Spring Boot defaults to 8080. Do not set the environment variable `RENDER` in IntelliJ. The Cloudinary keys must stay in environment variables, not `application.properties`.

6. Click **OK → Apply → OK**; run `CholoBodlaiApplication` (green triangle). After confirming no startup failure, open `http://localhost:8080`.

**Admin login reminder:** If an admin user already exists in MongoDB, `APP_ADMIN_PASSWORD` does NOT reset that account's password. Use the original password. Alternatively, choose a new unused admin phone to bootstrap a new admin account (do not share credentials).

## 2 — Connect Cloudinary (persistent media)

1. Log in to `https://console.cloudinary.com`.
2. Find **Cloud name**, **API key**, and **API secret** for your Cloudinary product environment (Settings / API Keys if not shown on your Dashboard). Do NOT paste the secret into GitHub or this chat.
3. Put those three values in your IntelliJ Environment variables, with `APP_MEDIA_BACKEND=cloudinary`. Run and try uploading a vehicle photo at `/trucks`.
4. A vehicle photo goes to Cloudinary as a public image in `cholobodlai/truck-photos/` and survives Render redeploys.
5. Owner registration documents go to `cholobodlai/truck-documents/` with Cloudinary's **authenticated** delivery type. Only the admin gets a **60-second signed** download URL after role authorization. Never change document upload type to `upload` (public).
6. If an old truck photo/document was uploaded to V5 on local disk, it will **not** automatically appear on Render. Log in as that owner and re-upload it to Cloudinary. Replacing a document must be re-approved by admin before that vehicle accepts bids again.
7. Supported media: vehicle photos JPG/PNG; registration documents JPG/PNG/PDF; max 5 MB. PDFs might require Cloudinary account security options for delivery; test a PDF download or use JPG/PNG documents.

You do **not** need to create an unsigned Cloudinary upload preset. Uploads are server-authorized using the API key/secret and HTTPS, never direct from the browser with exposed secrets.

## 3 — GitHub: push this source (private repository recommended)

1. In GitHub, create a **private** repo named `CholoBodlai-V6`. Leave automatic README and .gitignore generation off (the ZIP includes them).
2. In IntelliJ Terminal, `cd` into the **inner `CholoBodlai` folder that contains `pom.xml`**.
3. Confirm `.gitignore` excludes `uploads/`, `.idea/`, `target/`, `.env`, `application-local.properties` and other secrets.
4. Run:

```sh
git init
git branch -M main
git add .
git status --short
git commit -m "CholoBodlai V6: Render + Cloudinary"
git remote add origin https://github.com/YOUR_USERNAME/CholoBodlai-V6.git
git push -u origin main
```

Replace `YOUR_USERNAME`. If `git remote -v` already shows a remote, use `git remote set-url origin URL` instead of adding another. **Before `git push`**, confirm no secrets are listed in `git status` or tracked files.

GitHub Actions automatically runs Maven JUnit tests and independent policy/Cloudinary fake-server smoke tests after push. **Wait for the green CI check** before sharing the public link. A red failure requires fixing before deployment; source syntax checks alone do not guarantee compilation.

## 4 — Render: make the public site

1. Open `https://dashboard.render.com` → **New > Web Service**.
2. Connect your **GitHub** account and choose `CholoBodlai-V6`.
3. Enter:

| Field | Enter |
|---|---|
| **Name** | `cholobodlai-v6` (or another available name) |
| **Language / Runtime** | **Docker** |
| **Branch** | `main` |
| **Root directory** | Blank, if `Dockerfile` is at GitHub repo root |
| **Dockerfile path** | `./Dockerfile` |
| **Docker Command** | Blank, use Dockerfile ENTRYPOINT |
| **Instance** | Free for initial demo (if your memory usage fits) |
| **Region** | Singapore if offered (otherwise a nearby available region) |
| **Health check** | `/ping` |

You may instead use **New > Blueprint** with included `render.yaml`; it prompts for secrets. Do not create two web services accidentally.

4. Under **Environment**, configure these **Name / Value** entries. These are private Render environment variables, not project files:

| Name | Value / notes |
|---|---|
| `MONGODB_URI` | Your complete existing Atlas URI, including database name |
| `CLOUDINARY_CLOUD_NAME` | Real Cloudinary cloud name |
| `CLOUDINARY_API_KEY` | Real Cloudinary API key |
| `CLOUDINARY_API_SECRET` | Real Cloudinary API secret |
| `APP_MEDIA_BACKEND` | `cloudinary` **required for persistent uploads** |
| `APP_ADMIN_PHONE` | Existing admin phone or an unused number to create a new one |
| `APP_ADMIN_PASSWORD` | Existing admin bootstrap setting, 10+ chars (does NOT reset existing admin) |
| `APP_JWT_SECRET` | Long random secret: `openssl rand -hex 32` on your Mac |
| `APP_MAIL_PREVIEW` | `false` — NEVER enable the demo mailbox publicly |
| `APP_DEMO_SEED` | `false` — do not seed real Atlas data |
| `APP_COOKIE_SECURE` | `true` for HTTPS |
| `APP_PUBLIC_BASE_URL` | Exact HTTPS URL assigned by Render, e.g. `https://cholobodlai-v6.onrender.com` |
| `PORT` | `8080` (Render may supply its own, which is also supported) |
| `RESEND_API_KEY` | HTTPS email key, required for new signup & password recovery on Render Free |
| `APP_MAIL_FROM` | Sender from your **verified Resend domain** |

Do not set `APP_DOCUMENT_DIR` on Render; Cloudinary is permanent storage for new uploaded media. Do not set `APP_MAIL_PREVIEW=true`. Do not commit environment values.

5. On MongoDB Atlas, open **Security > Network Access** and allowlist your Render service's **outbound IP ranges** (Render Dashboard service > Connect / Outbound), then deploy. Avoid blanket `0.0.0.0/0` when targeted ranges are available.
6. Click **Deploy Web Service**. Render builds using your Dockerfile. Wait for a stable `Live` status and logs without `Application run failed`. Open the real `https://...onrender.com` hostname.
7. If service hostname differs from your planned name, update `APP_PUBLIC_BASE_URL` to the actual URL. This is what email verification and reset links use.
8. Test `/ping`, public `/`, secure login, admin, owner uploads, bid acceptance, tracking, and message/dispute/review permissions. Share the public URL only after the tests pass.

### Email requirement for a public audience

Render Free blocks outgoing SMTP connections on ports 25/465/587. V6 also supports **Resend via HTTPS** (`RESEND_API_KEY`) to send email verification/reset links without those ports. You must create a Resend account and verify a sending domain/address before you can email arbitrary customers. A Resend test sender without a verified domain may only send to a restricted recipient. If Resend is not configured, the public site can show its homepage and existing verified accounts can sign in, but **new registration is intentionally unavailable**, not silently accepted without verification.

### Security and file retention

- An admin's private document download link expires after 60 seconds; the document is Cloudinary `authenticated` media, unlike public vehicle photos.
- Cloudinary API keys, MongoDB passwords, mail keys, and JWT secret are never embedded in the ZIP or source.
- Existing MongoDB documents/booking history remain. V5's old local `uploads/` files do **not** automatically migrate to Cloudinary. Re-upload on the original computer where the old files still exist.
- Render may spin down Free instances when idle; first access after inactivity can take longer. Session cookies are secure over HTTPS; an idle instance restart may log users out.
- Deploying to Render is **not** a replacement for unit/integration testing. Validate CI, media upload, email, Atlas connection, and role access using the test checklist.

## 6 — Tests before publishing

1. In IntelliJ: **Maven > Lifecycle > test** or `./mvnw test` with internet access. Stop if it fails.
2. Run `sh qa/run-policy-smoke.sh` and `sh qa/run-cloudinary-smoke.sh`. Run `node qa/scroll-regression.test.cjs` if Node.js is installed.
3. Start locally, visit `/ping` (expect `ok`) and `/`.
4. Register and verify a shipper (admin-only local mailbox if preview mode). New Owner should stay pending until approved.
5. Upload a truck photo with Cloudinary and verify it shows on `/trucks` after a restart. Admin should be able to see private registration document; a shipper must not be able to access its admin URL.
6. Replace an already approved owner's document; check it becomes unverified and appears in `/admin` replacement review list. Verify it again and confirm bidding is possible.
7. Create/open/edit/cancel trips; test the 48-hour minimum booking rule and overly long/invalid inputs.
8. Bid twice as the same truck on the same trip (should update one bid); accept an offer; check the winning owner's other pending offers withdraw.
9. Confirm delivery steps, tracking simulator, private messages, disputes, reviews and receipts. Test a mobile viewport.
10. Deploy on Render; repeat signup and Forgot Password using **real Resend email**, upload a photo/document and check they survive redeployment.

**Verification limit:** This project was source-reviewed and its static/backend policy/Cloudinary fake-server smoke tests ran in the creation environment, but we couldn't run Maven dependency downloads or a real Render/Atlas/Cloudinary integration. Do not treat it as production-verified until your GitHub Actions checks and live end-to-end tests pass.
